Step by Step

Click any step to expand.

1
User Clicks Short URL
GET /abc123 -> Express router
▼

The redirect controller extracts IP, User-Agent, Referer from the request.

async redirect(req, res, next) { const { originalUrl } = await service.resolveUrl(shortCode, { ip: req.ip ?? null, userAgent: req.get('user-agent') ?? null, referer: req.get('referer') ?? null, }); res.redirect(302, originalUrl); }
Why 302? 301 is permanent - browsers cache it forever. 302 = temporary - every click hits us.
2
Build & Sanitize Click Event
Privacy: anonymize IP, strip referer queries
▼

buildClickEvent sanitizes raw request data.

function buildClickEvent(ctx) { return { eventType: 'url.clicked', ip: anonymizeIp(ctx.ip), // 192.168.1.100 -> 192.168.1.0 referer: cleanReferer(ctx.referer), // origin + path only }; }
Privacy: IPv4 /24, IPv6 /48. Referer query strings stripped (leak tokens). UA stored raw.
3
Outbox Append (Fire-and-Forget)
Staging area - redirect never waits
▼

The emitter appends to outbox_events. Fire-and-forget - 302 returns immediately.

// OutboxClickEmitter emit(event) { void this.outbox.append('url.clicked', event).catch((err) => { log('error', 'Outbox append failed'); }); }
Trade-off: Crash between redirect and INSERT = one click lost. Accepted - redirect latency beats analytics durability.
4
Publisher Claims & Publishes
Poll 2s, FOR UPDATE SKIP LOCKED
▼

Publisher polls outbox, locks rows, publishes with confirms, marks done.

// 1. Lock rows (no double-delivery) const claimed = await tx.select().from(outbox) .where(isNull(outbox.publishedAt)) .for('update', { skipLocked: true }); // 2. Publish with confirms channel.publish('shortly.events', 'url.clicked', buf, { persistent: true, messageId: row.eventId }); await channel.waitForConfirms(); // 3. Mark published await outbox.markPublishedBatch(ids);
Backoff: Failed claims: 2s, 4s, 8s... capped 1h. Crashed publisher rows auto-retry.
5
RabbitMQ Routes Message
Topic exchange -> queue -> DLQ for poison
▼

Message routed via shortly.events topic exchange to analytics.clicks queue.

Why topic? One routing key now, but adding more event types later requires no infrastructure change.
DLQ: Poison messages route to analytics.clicks.dlq. Prevents infinite requeue.
6
Worker Consumes & Batch Inserts
Micro-batch: 50 msgs or 100ms
▼

Consumer validates, micro-batches, inserts in one statement.

// Batch insert - one statement, not 50 await repo.recordClickBatch(events) // -> INSERT ... ON CONFLICT DO NOTHING // Publish to Redis for SSE void redis.publish(`analytics:click:${shortCode}`, payload); // Ack all for (const m of batch) channel.ack(m.msg);
Idempotent: ON CONFLICT DO NOTHING on event_id. Duplicates absorbed silently.
7
SSE Broadcasts to Dashboard
Redis pub/sub -> SSE manager -> clients
▼

Worker publishes to Redis pub/sub. SSE manager fetches full stats from PG, broadcasts.

subscriber.psubscribe('analytics:click:*'); subscriber.on('pmessage', (_, channel) => { const code = channel.replace('analytics:click:', ''); const stats = await service.getUrlAnalytics(code); for (const c of conns) c.res.write(`event: analytics\ndata: ${JSON.stringify(stats)}\n\n`); });
Why fetch from PG? Raw event = one click. Client needs full stats. PG is source of truth.

Failure Modes

Click any card to see impact.

🔴

Redis (Cache) Down

Cache unavailable during redirect

No data loss. Falls back to PostgreSQL. Redirect still works, slightly slower.
📦

Outbox Append Fails

INSERT throws

One click lost. Redirect succeeds (fire-and-forget). Documented trade-off.
📡

Publisher Crashes

Dies between claim and mark

No data loss. Unmarked rows re-claimed on restart.
🐇

RabbitMQ Down

Broker unreachable

No data loss. Publisher retries with backoff. Events wait in outbox.
⚙️

Worker Crashes

Dies before acking

No data loss. Unacked messages return to queue. Idempotent INSERT absorbs duplicates.
🐘

PostgreSQL Down

Analytics DB unreachable

No data loss. Worker nacks messages (requeue). Wait until PG recovers.
📡

Redis Pub/Sub Down

SSE bridge broken

Data safe in PG. SSE clients miss real-time updates. Reconnects when Redis recovers.
☠️

Poison Message

Malformed event

Isolated. Schema validation fails, reject to DLQ. Pipeline continues.

RabbitMQ Topology

Exchange: shortly.events (topic, durable) Binding: url.clicked → Queue: analytics.clicks Exchange: shortly.dlx (fanout, durable) Binding: # → Queue: analytics.clicks.dlq Queue: analytics.clicks durable: true, dead-letter-exchange: shortly.dlx

Key Indexes

-- Outbox: find pending rows fast CREATE INDEX idx_outbox_pending ON outbox_events (published_at) WHERE published_at IS NULL; -- Clicks: analytics queries ride this CREATE INDEX idx_click_events_link_time ON click_events (short_code, clicked_at);

Scaling Strategy

Stage 1: Single Process (Current)

[API + Publisher + Worker] → [PostgreSQL] [Redis] [RabbitMQ]
All three in one Node.js process. Works for low-to-moderate traffic.

Stage 2: Multiple API Instances

Nginx (load balancer) | +--------+--------+ | | | API #1 API #2 API #3 ← stateless | | | +--------+--------+ | [PostgreSQL] [Redis] [RabbitMQ]
APIs are stateless. Just copy the app. Nginx round-robins.

Stage 3: Separate Workers

API Servers Publisher Worker Analytics Worker | | | | [PostgreSQL] [RabbitMQ] | | | +--> [PG] +> [RabbitMQ] +> [PG] [Redis]

Stage 4: ClickHouse

At billions of events: 10x compression, 100x faster GROUP BY, 1M+ events/sec.
